Here's the authentication approach as built:

## Session model: JWT in an httpOnly cookie

**Token** — [security.py:21-27](backend/app/security.py#L21-L27): HS256 JWT signed with `settings.jwt_secret`, payload is just `{sub: user_id, exp}`. TTL is 7 days (`jwt_ttl_hours = 24 * 7`). No refresh token, no server-side session table — the cookie *is* the session.

**Cookie** — [security.py:30-40](backend/app/security.py#L30-L40): one `set_cookie` helper, `httponly=True`, `samesite="lax"`, `secure` from config (off in dev), `path="/"`, 30-day max-age. Cookie name `access_token`. Nothing auth-related touches localStorage, per non-negotiable #4.

**Passwords** — `bcrypt` directly (not passlib): `hashpw`/`gensalt` on register, `checkpw` on login.

## Reading the session

[deps.py](backend/app/deps.py) exposes a ladder of dependencies rather than middleware:

- `OptionalUser` — pulls the cookie, decodes, loads the `User`; returns `None` on any failure (`decode_token` swallows `InvalidTokenError`/`KeyError`/`ValueError`). Used by cart and anything with guest behaviour.
- `CurrentUser` — same, but 401s.
- `CurrentSeller` — [deps.py:44-53](backend/app/deps.py#L44-L53) deliberately splits 401 (not signed in) from 403 (signed in, no store), because the sell screen routes those two differently.

## Auth endpoints

[routers/auth.py](backend/app/routers/auth.py) — `register` (201), `login`, `logout` (204, just deletes the cookie), `me`. Both register and login funnel through `_sign_in`, which does two things in order: **merge the guest cart, then set the auth cookie**. Guests carry a `cart_token` cookie; on sign-in the guest cart merges into the user's (quantities add, capped at `MAX_QTY_PER_LINE`) and the guest cookie is dropped.

Login failures return one message for both unknown-email and wrong-password — no user enumeration. Duplicate email on register is a 409. Both endpoints are rate-limited via [ratelimit.py](backend/app/ratelimit.py) — an in-memory per-IP sliding window, marked `# ponytail:` as needing Redis if it ever runs multi-worker.

## Frontend side

The critical piece is [utils/api.ts:24-36](frontend/src/utils/api.ts#L24-L36) — non-negotiable #5. A `createIsomorphicFn` returns `undefined` on the client (the browser attaches cookies itself via `withCredentials: true`) and `getRequestHeader('cookie')` on the server, which an axios request interceptor forwards. Without that, every SSR fetch would hit the API unauthenticated.

Session state is a TanStack Query (`accountQuery`) hitting `/auth/me` with `.catch(() => null)` — a 401 is a legitimate "logged out", not an error state. Login/register mutations seed the cache with the returned user and invalidate the cart; logout clears the whole query client.

## Two things worth flagging

1. **CORS is an explicit allowlist** (`["http://localhost:3000"]`) with `allow_credentials=True` — correct, but it means cross-origin cookie flow is doing real work in dev. With `SameSite=Lax` and different *ports* on the same host, the cookie is still same-site, so it works; if the API ever moves to a different registrable domain in prod you'd need `SameSite=None; Secure`.
2. **`jwt_secret` has a dev default** in [config.py](backend/app/config.py) that ships in the code. It's clearly labelled `dev-only-insecure-secret-do-not-ship-me` and the README should say it must come from env in any real deploy — worth confirming `.env.example` covers it.

Short answer: **no — not for this build.** But there's a cheaper thing that captures most of what you'd actually want from it, and one real inconsistency worth fixing.

## What refresh tokens are actually for

The access/refresh split solves a problem created by *stateless* validation. You accept a token you can't revoke, so you make it short-lived (5–15 min) to bound the damage, and hand out a long-lived refresh token that lives somewhere more defensible and *can* be revoked.

Neither half of that applies here:

- **The token never leaves our cookie jar.** No third-party clients, no mobile app, no other service validating it offline. One audience, one origin.
- **We already hit the DB on every request.** [`optional_user`](backend/app/deps.py#L14-L19) does `session.get(User, user_id)` to resolve the token. We're paying the cost of a stateful session lookup *and* getting none of the benefit — which means we already have a revocation point sitting there unused.

Adding refresh tokens on top of a per-request DB lookup is paying twice for revocation.

## What it would actually cost

Done properly it's not just a `/auth/refresh` endpoint — it's rotation with reuse detection (without that, a stolen refresh token is strictly *worse* than today's 7-day JWT), a token table, and the concurrency case where five parallel requests all 401 at once and you need to queue-and-retry rather than fire five refreshes.

The part that would actually bite you is SSR. [`api.ts`](frontend/src/utils/api.ts#L24-L36) forwards the inbound cookie into server-side fetches. If a token expires *mid-render*, the server function has to refresh and then propagate a new `Set-Cookie` back out through the streamed response. That's fiddly, and it breaks in exactly the way that's hard to debug live.

## The 6-line version that gets you the real benefit

The one thing you're genuinely missing today is **revocation**. [`logout`](backend/app/routers/auth.py#L47-L49) only deletes the cookie — a token copied off the wire stays valid for its full 7 days, and changing a password invalidates nothing.

Since `optional_user` already loads the `User`, that's a `token_version: int = 0` column, the same value as a JWT claim, and one comparison in the dependency. Bump it on password change or "sign out everywhere". ~6 lines, no new endpoint, no frontend change, no SSR interaction. That's ~90% of the security value of refresh tokens for ~3% of the work.

## One thing that is a real inconsistency

`jwt_ttl_hours = 24 * 7` (7 days) but `COOKIE_MAX_AGE_SECONDS = 60 * 60 * 24 * 30` (30 days). For 23 days the browser holds a cookie the API will reject. It degrades gracefully — `/auth/me` 401s, the UI treats it as logged out — but it's an odd thing for a reviewer to notice. Deriving the cookie max-age from the JWT TTL is one line.
